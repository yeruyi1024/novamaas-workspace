# 对账数据底座：日志保留、增量汇总与凭证固化

设计基线：v0.3，2026-09-09，源码调研基线 `7c4d7aa`。本文保留批准开发前的完整方案；用户随后批准收敛到管理员与下游客户消费对账的一期开发，实际实现与未纳入本期的扩展能力以 [实施与验收说明](BILLING_STATEMENTS_IMPLEMENTATION.zh_CN.md) 为准。

配套：[产品方案](BILLING_STATEMENTS_PRD.zh_CN.md)、[技术总方案](BILLING_STATEMENTS_TECH.zh_CN.md)。本文补齐用户提出的三项技术疑问，不代表已经修改生产日志设置、安装中间件或验证性能。

## 1. 结论与选型

建议采用 **MySQL 同库可靠记账 + 持久增量汇总 + 按日逐笔封存 + 月单不可变清单/PDF**。现有 Redis 仅用于查询缓存及唤醒提示；大规模明细文件推荐私有 OSS，不强制引入 Kafka、Flink、ClickHouse 或 Elasticsearch。

| 已确认条件 | 本版处理 |
| --- | --- |
| 钱都来自管理员充值，不使用赠送/订阅 | 单一消费口径；充值、扣减、覆盖余额独立留结构化资金依据，不当成消费 |
| 上海时区、入账时间、自然月、24 小时缓冲 | 时间由服务端判定；迟到结算/退款记实际入账期，不回写已封账月份 |
| 管理员配置每用户正式记账起点 | `accounting_start_at` 精确到时刻，技术采集起点另存，不擅自替换配置值 |
| 用户维护企业抬头、税号 | 资料有版本，下发绑定当时值；以后修改不影响旧单 |
| 使用日志不能清理 | 持续记录、永久保留；封住 UI/API/后台删除/关闭记录/TTL，不仅保留 PDF |
| 生产数据目前最多约千条，日常最大预计万级 | 以 1 万请求/日为日常设计基线，100 万请求/日为容量验证目标 |
| 当前 MySQL，可引入中间件 | 优先保证同库事务；对象存储解决大文件保存，缓存不承担账务正确性 |

百万请求/日平均约 11.6 请求/秒，不代表峰值只有这个量。以下批次大小、并发和延迟均为初始设计/测试值，实际数据库版本、硬件、峰值和账户分布尚未核实。

## 2. 当前日志能否清理：源码证据与整改边界

### 2.1 确实存在，但不能据此推断生产已经执行过

| 层级 | 证据 | 当前行为 |
| --- | --- | --- |
| 页面 | [log-settings-section.tsx](../../web/src/features/system-settings/maintenance/log-settings-section.tsx)，`LogConsumeEnabled` / `Clean history logs` | 可关闭消费记录，并按时间发起历史日志清理 |
| 路由 | [api-router.go](../../router/api-router.go)，`/system-task/log-cleanup` | `POST /api/system-task/log-cleanup`，仅 root 可调用 |
| 后台任务 | [system_task.go](../../service/system_task.go)，`runLogCleanupTask` | 重复调用删除函数，重启后持久任务仍需处理 |
| 实际删除 | [log.go](../../model/log.go)，`DeleteOldLogBatch` | 按 `created_at < target` 删除，没有豁免消费或退款类型 |
| 记录开关 | [log.go](../../model/log.go)，`RecordConsumeLog` | 开关关闭时直接返回；写入失败目前可能只记错误 |
| 可选日志数据库 | [main.go](../../model/main.go)，`clickHouseLogTTLDays` / `syncClickHouseLogTTL` | ClickHouse TTL 可配置自动删除，默认值为 0；这不是 MySQL 默认自动过期能力 |

生产主库是 MySQL；尚未检查生产是否另设 LOG_DB、清理任务是否运行、实际保留范围和 DBA 任务。因此结论是“代码存在删除能力”，不是“你的生产使用日志已被删除”。

### 2.2 新约束必须逐层落实

1. 页面不再提供关闭使用记录、清理历史使用日志的操作，明确展示永久保留政策。
2. API 拒绝旧客户端的关闭/清理请求；权限是 root 也不能绕过这一业务约束。
3. 调度器不再领取旧清理任务；升级时处理 pending/running 的遗留任务，并阻止旧版本节点继续执行删除。
4. model 层删除入口移除或明确拒绝执行，杜绝内部调用绕过 controller。审计失败尝试，但不记录敏感载荷。
5. 禁止日志表 TTL。升级核查已有规则，而不仅设置默认值；MySQL 的外部事件、运维脚本和对象生命周期同样需要只读排查、按审批流程调整。
6. 应用数据库账号遵循最小权限：usage/账务/凭证表不授予日常 DELETE；账务事实不授予日常 UPDATE，投影和工作状态使用受限的独立权限。迁移使用单独账号，不与运行时自动迁移权限混用。
7. 使用日志、原始账务事实、已封存明细、PDF、确认/异议事件均不级联删除，不因用户停用或账号软删除而失去历史归属。

应用限制无法阻止拥有数据库超级权限的人手工删表，需要权限分离、独立备份和不可覆盖存储共同防护。本文未执行任何上述生产变更。

“使用日志”与程序运行诊断文件不同。诊断文件可另行讨论轮转，但不能借轮转删除使用记录。请求正文是否采集继续遵循既有隐私配置，不把密钥、提示词扩大采集到财务档案；已采集使用记录的保留要求不能被正文存储生命周期间接绕过。

### 2.3 不能只保证不删除，还要防止没有写进去

结算时将最小使用记录连同稳定 `event_id` 写入主库 outbox；同库 LOG_DB 可以直接事务写入，分库时由后台持久投递。日志库短暂失败保留待办并重试，不能只输出一条错误然后丢失调用记录。投递延迟独立告警，页面区分未投递与没有调用。

成功、零费用、失败或中断的已接纳逻辑调用都需要可追溯终态；上游结果未知则明确保存未知，不能伪造用量为零。调用接纳前的未认证 HTTP 流量不作为本功能的用户消费事实。

MySQL 日志落点可用事件唯一键去重。若日志落点为 ClickHouse，需要单独验证其投递去重语义，不能把可重试投递宣称为数据库强唯一；正式账务总额始终来自主库去重账务事实，不对可能重复投递的日志直接求和。确认已持久投递不意味着允许删除使用数据，工作状态与需要保留的原始载荷分开设计。

## 3. 先保证账务事实，再讨论汇总

### 3.1 事实边界

新增账务记录不替换现有模型定价，不在出单时重跑 billingexpr。记录的是现有规则已经确定并实际入账的 quota；单次额度继续遵循现有溢出、NaN 和非负计费防护。

```text
持久接纳逻辑调用 → 事务预留资金 → 调用上游 → 持久保存可确定结果
                                              ↓
主库短事务：资金差额 + 资金凭据 + 消费 entry + 使用记录待办 + 汇总待办
                                              ↓
                              后台增量汇总 / 日封存 / 日志投递
```

“请求实时记录”不意味着读页面时应实时扫描请求表。请求链路负责小而有界的可靠写入，复杂归集和文件生成在后台执行。

### 3.2 同事务与幂等协议

- 内部 `operation_key` 由服务端生成，同一逻辑调用跨重试保持稳定；客户端 Request ID 只是追踪字段，不能作为扣费去重的唯一依据。
- 预扣和 operation 在同一主库事务落地，上游调用在事务外；主库无法接纳时不先发出新的收费调用。
- 结果确定后持久保存目标 quota/修订号；按统一账户 → 操作 → 资金/任务顺序锁定并核验，把资金差额、资金凭据、消费 entry、账户序号、汇总队列目标、使用记录 outbox 一起提交。
- 用业务唯一键约束 `(user_id, operation_key, revision)`，事务重试先核对已提交结果。提交返回不确定时按同一键查询，不生成新键再次扣款。
- 在账户锁内分配 `account_seq = last_entry_seq + 1`，与 entry 同事务提交。事务失败不推进序号，不用全库自增 ID 的最大值代替提交水位。
- 预扣 10、最终 7：最终消费 entry 为 7，释放的 3 是资金动作，不再成为消费退款。预扣 10、最终 10 也要有消费 entry，不能因差额为零提前跳过。
- 已实际入账的任务初始消费、终态补扣、消费退款各有独立修订和原业务引用。退款额度存非负绝对值，以类型/方向表示；一笔逻辑调用只增加一次调用数。
- 管理员充值、扣减、覆盖余额也走资金事务和幂等键。覆盖余额以锁定后的真实余额算差额；不把“充值 100、消费 8”汇总成消费 108 或负 92。

跨表必须使用同一个 `tx`；后台缓存更新与 Token 统计失败不能再次扣费或误退资金。现有 Redis 优先扣减和进程内资金批次在可靠路径中需要调整；只在日志旁新增一张表，无法获得这些保证。

### 3.3 无法凭空恢复的窗口

上游已响应、进程尚未保存用量就崩溃时，无法仅靠本地消息队列推导真实用量。之前持久接纳的 operation 保留为 `needs_review`，通过可靠上游结果/任务状态恢复；不能恢复就由管理员核查，阻止受影响账期出单。不要自动重放一次可能再次收费的上游请求来“补日志”。

可见状态必须是“结果已可靠入账”“正常等待结算”或“结果不明需处理”之一，不允许把不明状态当成零金额。正常在途任务未来结算计未来入账期；结果不明和已知漏账才是完整性阻断问题。

### 3.4 从旧资金路径切换

切换前在受控窗口暂停新的旧路径资金变动，排空进程内批次并等短请求完成；核对数据库余额、旧缓存与实际预留情况，保存带来源和校验结果的资金基准。恢复流量前确认所有写节点采用新协议，不能让旧节点继续在旁路扣费。

较长的异步任务不能假定已经全部结束。逐项登记其已扣额度、来源、当前阶段和稳定任务 ID，以带批次的迁移操作接管后续结算：已有初始扣费不是一次新的消费/充值，后续只提交真实调整。缺少可靠已扣依据的事项进入待核查，不能靠推测建立无差异基准。未经验证，不开启对应账户完整覆盖声明。

`billing_coverage_intervals` 记录完整区间、切换/回退中断和经核查补录区间。最早一条日志、最早一笔 entry 或单一 `capture_start_at` 不能证明中间没有缺口。隐藏对账页面不停止采集；若回退到旧资金路径，需明确记录新缺口并暂停相关正式出单，不能删除已有事实。

## 4. 增量汇总：让查询成本不随请求量线性增长

### 4.1 为什么现有统计不能直接承担正式对账

[model/usedata.go](../../model/usedata.go) 的 `CacheQuotaData` 是进程内 map，周期调用 `SaveQuotaDataCache`；它受 `DataExportEnabled` 控制，含模型、Token、渠道、节点等多个维度。消费/退款的现有汇总口径也不完整。进程重启与失败落库不能依靠它证明没有遗漏。

新投影独立建立，旧看板无需在本轮被替换。增量汇总仍然使用 SQL，但只对有索引的新数据做有界读取与更新，不在每次开页面时重新 GROUP BY 全月日志。

### 4.2 每账户 checkpoint 与持久合并队列

1. entry 提交事务把 `billing_projection_queue.target_seq` 推进到新的账户序号；每账户最多一个当前待办。Redis Pub/Sub 若使用，只是加速唤醒，不是唯一任务来源。
2. worker 用短事务和带版本的租约领取账户，锁立即释放；MySQL 5.7 不依赖 `SKIP LOCKED`，使用条件更新/CAS 领取，三库均验证。
3. 读取 `(user_id, account_seq > checkpoint)` 最多 1000 条，按账户序号排序并验证连续；发现缺口停止并报警，不跳过。
4. 在内存中仅聚合该批次，生成少量小时/日增量。消费、退款、调用数分别累加，只有消费净额是两者之差；不得把方向编码成可能溢出的负扣费。
5. 短事务中核验 checkpoint、generation 与租约代次，再更新小时/日表和 checkpoint。CAS 失败必须回滚整批，不能留下已经累加但游标没动的结果。
6. 完成时只有 `target_seq <= applied_seq` 才条件标为已追平；新 entry 并发推进目标时不能无条件清空待办。租约过期的旧 worker 不能提交新任期的工作。

任务语义是可重试处理，正确性由数据库唯一约束、事务和 checkpoint 保证，不依赖“消息绝不会重复”。worker 不在账户资金锁上做长扫描；投影表可以重建，资金事实不能改写。

初始建议：调度 1–5 秒、每批不超过 1000 条、2–4 个 worker；每账户处理一个批次后公平让出，避免热账户饿死其他账户。限制 DB 连接占用及每秒处理量，让请求结算优先，不能用无限并发把后台积压转成前台超时。

### 4.3 查询路径与一致性

| 功能 | 读取来源 | 数据量边界 |
| --- | --- | --- |
| 指定日小时账单 | 当前 generation 的小时投影 | 上海时区最多 24 行，加少量状态/首小时边界行 |
| 月汇总预览 | 日投影 | 最多 31 行，正式起点当天用准确边界结果 |
| 实时调用下钻 | 有索引的 immutable entries | 默认 20、上限 100，游标分页，不使用深 OFFSET |
| 已下发单据正文 | 固定 snapshot | 一份小正文，包含最多 31 日及 744 小时行 |
| 已下发单据逐笔下钻 | 清单索引与固化明细块 | 一至少量块；按日期和块内位置分页 |
| PDF 下载 | 固定 artifact | 返回原字节，不重新查询日志或渲染 |

小时、日、checkpoint、generation 在一个提交边界更新。动态查询采用主库上的短一致性读取；兼容实现可按“读版本 r1 → 读投影 → 读版本 r2”执行独立新鲜读取，只有 r1=r2 才返回，最多重试两次，否则提示处理中。不能混用不同复制延迟的读副本或把两个版本读放进同一旧快照，而数据却从别处读取。

另一合法实现是在同一连接上显式开启受支持的短只读一致性快照事务；必须逐库验证隔离级别，不假设默认事务一定能固定多个 SELECT。PostgreSQL 默认 Read Committed 下连续查询可能看到不同提交状态。[PostgreSQL 9.6 官方隔离级别说明](https://www.postgresql.org/docs/9.6/transaction-iso.html)。

不在 HTTP 请求上补扫未投影尾部。正常展示短暂延迟和真实截至水位；延迟超阈值显示异常/处理中，不能显示一个貌似完整的最新数。没有新请求的安静账户也不应仅因“最近 entry 很旧”就被判为延迟，延迟基于待应用序号及最老未处理事件计算。

Redis 缓存键含用户、日期、起点策略、币种配置和投影版本；鉴权先于缓存读取，缓存失效不影响事实。历史关闭日期可稳定缓存；实时页短缓存并返回同一数据截至信息。页面 30 秒刷新不等于后台必须每 30 秒扫描明细。

### 4.4 重建与修复

发现投影 bug 时用新 `generation` 从 immutable entries 限速重放，老代继续服务并显示核查状态。追平固定水位、逐桶核对后短事务切换当前代，不能先清空正在被查询的汇总表。复核不匹配的账期暂停正式下发。

定期核对按账户/日期分批执行；不安排每分钟全库从头 SUM。已出具单据不会跟随投影重建改变，若单据本身需要更正遵循产品的版本/作废规则。

## 5. 正式记账时间、封账与主体资料

### 5.1 两个时间不能混用

`capture_start_at` 表示全节点可靠采集协议生效、可提供完整依据的技术起点；`accounting_start_at` 是管理员为该用户设置的业务起点。账户未设置业务起点也继续可靠采集，未正式启用不等于允许丢弃调用证据。

- 未配置：不出具正式对账单，账单页面提示管理员配置；现有使用日志查询仍可用。
- 配置未来时间：保存准确值，到时纳入；未到时不虚构零金额已结账区间。
- 配置过去时间：验证该时刻起连续覆盖、版本/资金来源明确、无未知缺口。若不满足，拒绝该配置生效并提示缺口；不擅自改成更晚的起点。
- 首单下发前修改：使用策略版本防并发，失效旧预览，后台重建首小时边界；原始 entries 不删除、不改日期。
- 首单下发后：普通用户管理编辑锁定此字段。确需历史更正另行设计有审计的流程，不在一期做一个可绕过的强制开关。

例如起点是 9 月 15 日 10:30，只纳入 `posted_at >= 10:30`。后台为第一个小时构建截取汇总，首日等于这段 10:30–11:00 加后续完整小时。不能用 10:00 的整小时代替，也不在每次查询首日时扫描全部记录。首次配置落在正在进行的小时，边界投影随新 entry 增量推进，并与普通投影共享可验证的 checkpoint。

首月实际范围为 `[accounting_start_at, 下月 1 日 00:00)`；前几日是“不纳入”，不是“数据缺失”或“消费为零”。正式起点前的消费在起点后发生退款时，按退款入账时间计入，并携带原始发生时间/引用及跨范围说明，不能因原消费不在本期而丢掉实际退款。

### 5.2 固定日边界与月边界

入账时间由服务端在资金事务内确定，不接受客户端回填；在账户串行提交边界内保证入账顺序不倒退，并记录 `occurred_at` 供追溯。时间服务须同步，监控节点/数据库时钟偏差；遇到跨已关闭边界的回退或异常未来时间时阻断核查，不能默默把错误时钟纳入封账。

日结束后，短事务取得与入账相同的账户锁，记录该日固定截止水位与关闭标识；月结束及缓冲满足后同样固定月边界。正常新写入只能进入其实际开放入账期，关闭期禁止新增或回填；不是依赖“过了 24 小时大概不会再有数据”来保证不变。

锁释放后等待投影应用至该关闭水位，再用稳定范围封存，整个文件生成阶段不持有资金锁。已经开始但未结束的请求后来结算计后来入账期；异步任务初始已入账则保留初始额，未来调整另记当前期。已知缺失或结果不明的 operation 会阻断受影响账期正式出单，正常等待结果须在核对说明中披露。

关闭状态、截止序号、策略版本和异常版本一起构成可验证边界；不能只使用 `MAX(log.id)`、服务器当前时间或一条 `COUNT(*)` 声称期间完整。迟到的已确定资金结果也不回写已关闭期，保存原发生时间与关联记录。

### 5.3 企业主体

用户通过所有者专用接口维护企业名称和税号，每次保存追加资料版本并推进当前指针。税号按有长度上限的字符串处理，保留前导零；格式校验不等于已验证企业真实身份。字段不进入公共用户列表、登录 token 或不必要缓存。

管理员在用户管理界面设置正式记账起点时调用带版本的专用策略接口；主体资料与起点权限分开，防止用户更新企业资料时顺带修改记账范围。管理员代维护企业主体应使用明确的授权动作和审计，不能静默冒充用户。

预览取当前资料版本，最终下发检查版本未变；正文保存企业名称、税号和出具主体的当时值。以后修改只影响新单，已下发单据仍绑定旧主体；确认者的登录身份另外存档，不能把企业抬头当成实际点击确认的人。

## 6. 逐笔固化：保存完整内容，不只保存查询条件

### 6.1 四层固定数据

| 层次 | 保存什么 | 是否依赖当前业务表重算 |
| --- | --- | --- |
| 原始账务事实 | 主库 entry、资金凭据、操作修订；不可变 | 不按现行费率回算，是核查来源 |
| 日逐笔明细集 | 全部纳入 entry 的规范化内容，分块文件及清单 | 否；单据可直接读文件 |
| 月单正文与 manifest | 精确范围、日集引用、汇总、币种/汇率/精度、企业主体、模板规则 | 否；成员集合和解释规则冻结 |
| PDF 与确认事件 | 原始 PDF 字节、正文/清单/文件哈希，真实确认主体与时间 | 否；确认后文件单独生成，旧文件保留 |

明细集不是数据表的动态视图，也不是一串以后重新执行的 SQL。独立保存逐笔内容使已出具单据不依赖可变账户资料或当前数据库行的展示拼装；主库源记录仍永久保留，封存不触发源记录删除。

### 6.2 每条固化记录的最小完整内容

保存 `schema_version`、`entry_id`、账户序号、逻辑业务 ID、操作修订、用户稳定 ID、`posted_at`、`occurred_at`、费用类别/方向、原始 `amount_quota` 和单位版本、首次调用标志、模型/业务名称快照、必要用量与费用说明、原消费/任务引用及跨期原因。

费用说明需足以解释最终扣额：定价规则/版本引用和本次已确定的计费参数摘要在记账时保存，归档原样固定，不在归档阶段从“当前费率表”补写；不能因费率后改而重新算一次。敏感渠道成本、密钥、提示词、完整上游正文及审计 IP 不进入用户可读明细集。用户查看使用日志是额外追踪入口，不是显示单据金额的必要条件。

quota、累计额度、序号和货币数值以规范十进制字符串存档；时间和排序规则固定到 schema。所有 JSON 操作经项目 `common.*` 封装，序列化使用显式结构及稳定字段顺序，扩展 map 先规范排序，不依赖语言 map 的遍历顺序。

### 6.3 每天封存，摊平月末成本

1. 日关闭水位固定、投影追平后创建 `billing_detail_sets` 作业，状态为 `building`。按 `(user_id, posted_at, account_seq)` 索引和固定起止范围读取，不使用无上限 `Find` 或深 OFFSET。
2. 每次读取最多 1000 条，流式生成规范记录；每块建议最多 5000 条且未压缩不超过 8 MiB，任一条件达到即封块。单条说明字段在写入前有长度上限，不能靠静默截断完成归档。
3. 每块保存覆盖范围、首末序号、笔数、消费/退款额度、调用数、规范内容哈希与压缩文件哈希，采用固定版本的 gzip 编码。压缩参数/时间头确定化；读取时限制解压大小，防止异常文件耗尽内存。
4. 块上传至私有、不可覆盖的对象键，校验实际保存字节；数据库以唯一 `(set_id, chunk_index)` 登记。失败后重试同一作业/块，只复用内容一致的已完成结果，不能修改已封存块。
5. 验证全部块顺序、无重复/遗漏、笔数与额度，并与稳定范围内的 entry/小时/日结果核对。通过后固化日集 manifest/root hash，状态变为 `sealed`；记录校验算法版本和结果。
6. 月单只组合最多 31 个已封存日集的根引用及小型汇总。manifest 保留有序成员关系，不按月重复复制全部逐笔文件；日集内部再索引块，避免每次打开月单加载几千块的元数据。

按日处理仍有 O(N) 扫描、序列化和存储成本，但每笔只进入有限次后台处理，工作可限速、续跑并分散到每天。日封存落后时月单显示具体积压；不能把“尚未准备”当成已经下发。

封存读固定不可变范围，因此不需要保持数小时数据库一致性事务。分页进度仅在块保存并登记后推进；作业租约带代次，过期 worker 无法把旧结果覆盖为完成。对象保存成功、DB 登记失败时重试核对相同对象，不重新决定成员集合。

### 6.4 首期边界、零数据与重发复用

首期起点在日中时，第一日生成专属于该准确起点的截取集，其余完整日复用已有日集。可以从已封存日块提取；只有边界部分需要生成新的块，不能把整日总额直接写到首期。账单 manifest 指定确切集 ID/根哈希，不能让未纳入的记录泄露为该账单明细。

完整覆盖但没有 entry 的日子保存明确的零记录清单及覆盖边界，不以“找不到文件”代表零消费。存在未知缺口、未完成块或校验错误则不能封存为完整。

同一批费用因企业抬头纠正而重发，可复用不可变日明细集，重新生成月 manifest/正文/PDF。汇总算法修复要产生新投影/校验版本；实际资金更正新增当前入账期 entry。旧单、旧清单及旧确认事件不覆盖。

### 6.5 原始额度与金额的冻结方式

日明细块保存不可变的 quota 和计费解释，不提前绑定将来下发时才确定的展示汇率，因而能被不同单据修订安全复用。月单 manifest 冻结 `quota_per_unit`、币种代码/名称/符号、十进制汇率、金额精度、舍入方法、格式及算法版本；正文固定每个日/小时的原始额度与展示金额。

逐笔接口由服务端按固定额度与该单固定的十进制规则产生金额字符串，前端只展示，不读取当前系统汇率或价格。这是解释已固定的数据，不是重新定价或查询实时源明细。版本升级必须保留历史格式解释器及测试样本；不得用新版本默认规则重解释旧单。

先按精确 quota 汇总再转换总额。逐笔/日行显示舍入后可能与上一级相差最小显示单位，返回明确 `rounding_adjustment`；不能偷偷修改某笔费用平账。大规模累加使用精确十进制或受检查整数，不能调用单请求 int32 饱和函数截断月度总额。

### 6.6 如何证明“没有漏掉一块”

只核对消费总额不够，一增一减同时漏掉可能净额仍一致。封存过程中独立累计记录数、调用数、消费总额、退款总额、净额，并校验账户序号顺序和范围；规范记录流再生成有序内容摘要。

manifest 显式列出每个块/日集的顺序、哈希、大小、笔数和额度，包含用户、准确账期、起点策略、单位版本及固定截止水位。校验链为“资金操作 ↔ entry → 日封存完整记录流 ↔ 小时/日投影 → 月 manifest → 正文/PDF”。摘要校验保护已经固定的集合，源头接入完整性仍需靠操作协议和异常核查，不能由文件哈希单独证明。

## 7. 下发与确认：完整准备之后一次性发布

### 7.1 下发准备与提交

草稿每次重新生成分配独立 `content_version`，候选正文、manifest 和 artifact 都绑定这个版本；单据修订号与候选内容版本不是同一个概念。已有文件不被新一次生成覆盖，下发时原子选择本次完成的内容版本，避免旧渲染任务晚到把新草稿替换掉。

管理员预览只读小型汇总；保存草稿后后台完成以下工作：

1. 固定目标账期版本和边界，核对正式起点、主体资料、货币配置与完整性。
2. 确认每个日/首期截取集已封存，建立月 manifest，核对消费/退款/笔数和日小时合计。
3. 固定正文及金额快照，生成原始 PDF，保存并计算文件哈希；文件字节保存失败不能进入 `ready`。
4. 最终短事务重新验证权限、账期/草稿版本、资料和配置版本、异常状态、manifest 与 artifact 的完成凭据；成功后设为 `issued`，更新账期有效指针，并写下发事件/通知 outbox。

耗时的扫描、压缩、上传、PDF 渲染全部在最终事务之外。交易锁内只核对已经完成的结果，没有“锁住用户钱包直到整月 PDF 生成完”的步骤。

若渲染期间用户改了税号、管理员改了起点、货币设置改变或权限被撤销，最终提交拒绝并要求重新核对，不自动替管理员接受新的金额。其他月份正常新调用不改变目标已关闭期的数据版本，不能造成无限预览失效。

正式状态只在整套内容成功持久化后对用户可见。通知发送与业务下发分开；通知失败重试，不生成另一张新账单。

### 7.2 确认绑定四类信息

| 信息 | 作用 |
| --- | --- |
| `manifest_sha256` | 绑定完整明细成员、原始数据及固定金额解释规则 |
| `content_sha256` | 绑定企业/出具主体、账期、明细清单、汇总、声明与模板正文 |
| `issued_pdf_sha256` | 绑定用户可下载的原始 PDF 字节 |
| 确认事件 | 绑定真实所有者、单号/版本及上述哈希、服务器 UTC 时间、声明全文/版本、最小会话审计 |

用户通过真实所有者会话主动确认当前 `issued` 版本；后台校验客户端回传哈希，不接受浏览器上传的时间或金额。确认事务锁定单据并用版本条件修改状态，与管理员作废互斥；重试返回同一事件和时间。

确认事件先可靠提交，再异步生成包含原单与确认记录的新 PDF。新 PDF 绑定该确认事件，原始 PDF 仍然保留；确认后 PDF 生成失败不会撤销确认，用户看到“确认成功，确认记录文件生成中/待重试”。

哈希不能包含自身或未来确认文件哈希造成循环依赖。正文绑定 manifest，原始 PDF 绑定正文；确认事件绑定前三者；确认 PDF 绑定正文与确认事件。状态/通知/下载次数不参与原正文哈希。

## 8. 数据有效性：事务、校验、存储保护缺一不可

### 8.1 三种保证的边界

| 保证 | 解决的问题 | 不能单独解决的问题 |
| --- | --- | --- |
| 主库事务、幂等键、持久操作 | 重复扣费、账务写一半、结果不明不可见 | 不能还原从未收到/持久保存的上游用量 |
| 笔数/金额勾稽、规范内容哈希、不可变版本 | 重放重复、漏块、损坏、确认错版本 | 超级管理员同时改数据和哈希仍需外部证据防护 |
| 权限分离、不可覆盖存储、独立备份与恢复演练 | 误删、覆盖、介质故障和单一管理员权限风险 | 不自动变成法定电子签章，也不保证无限保留无需成本 |

确认记录是本平台的业务凭据，不宣称等同银行回单、税务发票、第三方可信时间戳或独立电子签名认证。用户企业资料为自维护信息，其真实性验证是另一个产品流程。

### 8.2 存储方案

小规模部署可将小型 PDF 和有上限的明细块放入主库独立 BLOB 表，元数据查询不加载大字段。单 PDF 初始上限建议 5 MiB，排版原型验证后确定；百万逐笔明细不进入主 PDF。禁止仅存某个节点本地目录，避免容器重建或跨节点下载后文件丢失。

百万请求/日目标推荐将压缩明细块及较大 artifact 放私有 OSS，MySQL 留清单、哈希、对象版本/定位信息和索引。现有项目仅阿里云 OSS 驱动已经实现；仍需开发账单专用的不可覆盖写入、校验与下载适配，不能直接复用会过期的媒体文件管理流程。

对象名使用不可预测标识或内容寻址；禁止覆盖完成对象，若使用存储版本能力，数据库必须绑定明确 object version，而非以后可能指向别的字节的“最新版本”。下载每次做用户/单据鉴权，可后端流式返回；知道 URL、单号或文件哈希都不代表有权访问。

建议在正式环境评估独立的归档存储权限与 WORM 保留保护。阿里云官方说明，锁定保留策略后，在保留期间受保护对象不能被修改/删除，保留期只能延长不能缩短；这类锁定涉及不可逆约束，需专门审批和验证，不在本轮自动配置。[OSS 官方保留策略说明](https://www.alibabacloud.com/help/en/oss/user-guide/oss-retention-policies)。

WORM 的有限保护期不等于产品要求的永久保留；保护期满也不得由应用自动清理。费用欠付、凭据丢失和灾害仍需运营措施与独立副本，不能把一个存储开关当成永久有效性的全部保证。

### 8.3 备份、恢复与完整性巡检

- 检查生产 MySQL 的事务引擎、提交持久性、复制与故障切换设置；在未验证这些配置前，不声称任意故障下零数据丢失。
- 数据库备份覆盖 operations、资金凭据、entries、配置/主体版本、manifest、状态事件及主库存档；对象存储有独立故障域的保护副本，权限和删除权限与应用隔离。
- 发布顺序为对象先持久化、数据库再发布引用，避免用户看到尚未上传的正式文件；这不等于数据库与 OSS 具有分布式原子事务。
- 备份记录可恢复的数据截止点及对象清单。恢复后先验证所有已发布引用存在、哈希相同、确认事件可读，再恢复正式出单；单独恢复数据库到过去某点不能推断对象/通知/缓存也自动回退到一致状态。
- 一般下载校验文件大小和哈希，明细读取校验块；后台按计划轮转校验所有封存内容，记录检查进度和损坏告警，不只抽查最近几张 PDF。
- 缺失或损坏时从可信副本恢复相同字节/哈希。不能用当前汇率重画一份 PDF 冒充原件；无法恢复原件时标记完整性事件，并暂停有关操作。
- 在独立环境演练主库恢复、对象恢复、全部引用核验和后台重放。RPO/RTO 根据部署能力与演练结果确认；正式下发前必须有可执行、已验证的恢复流程。

## 9. 故障与并发处置矩阵

| 场景 | 正确行为 | 对外影响 |
| --- | --- | --- |
| 主库在调用接纳前不可用 | 不把预扣或请求接纳只写内存/Redis | 新收费请求明确失败，不造成无记录上游消费 |
| 上游结果已返回但尚未持久化就崩溃 | 既有 operation 标记待核查，从可靠来源恢复 | 受影响账期阻止正式出单，不假定用量为零 |
| 事务提交成功但客户端超时重试 | 同业务键查询原结果，资金和 entry 不再应用 | 原消费及原时间保持 |
| Redis 宕机、丢消息、旧缓存 | 主库资金事实继续有效；缓存失效/降级 | 查询可能变慢，不漏账、不重扣 |
| 日志库分离且暂时不可写 | 主库持久 outbox 重试 | 使用日志投递延迟可见，账务不丢 |
| worker 处理后、checkpoint 提交前崩溃 | 整批同事务回滚，重新处理 | 不重复累加；汇总短暂落后 |
| worker 租约过期、新旧 worker 并发 | 任期/CAS 拒绝旧提交 | 同一批只生效一次 |
| 汇总落后或重建中 | 返回正确截至边界，后台追平/新代校验 | 可显示最近完整结果；正式出单等待 |
| 日封存中断、对象保存后 DB 写入失败 | 从已登记块续跑，校验同内容后重用对象 | 草稿显示准备中/失败，不提前 issued |
| 单块缺失、顺序/哈希/额度不一致 | 阻止 sealed/issued，保留错误供定位 | 不发送不完整单据 |
| 下发过程中抬头、税号或货币配置改变 | 最终版本校验失败，重新预览 | 用户不会收到混合版本 |
| 另一月份出现新消费 | 目标已关闭期不变化 | 不误判旧月份预览过期 |
| 用户确认与管理员作废并发 | 同一状态/版本条件，只允许一个成功 | 另一方刷新并看到实际结果 |
| 确认成功但确认 PDF 生成失败 | 保留确认事件，单独重试新文件 | 确认仍有效，原 PDF 仍可下载 |
| 外部邮件发送后进程未保存结果 | 渠道幂等支持则复用；否则可能重复提醒 | 不重复创建单据，不把已提交渠道当成已送达 |
| 账户停用、资料后改、投影升级 | 身份引用、档案和确认快照保持 | 管理员可审计历史，不冒充所有者确认 |

所有长任务必须有退避重试、上限告警和人工恢复入口，不能无限静默重试。账务异常不能通过一个“忽略错误继续下发”的按钮变成完整证据。

## 10. 容量预算与压测计划

### 10.1 基本预算

设每日请求量为 R，每个请求平均产生 E 条账务事件；任务补扣/退款会使 E 大于 1。写入预算按 `R × E` 而不是只按请求条数估计；每个事务还包含资金记录、outbox、索引、redo/binlog 等成本。

以 E=1、单条原始账务记录平均 500 字节为纯示意：100 万条/日约 500 MB/日、182.5 GB/年，仅是账务行净数据；不含使用日志、索引、operation/资金凭据、压缩归档、复制及备份。实际字段尤其费用说明可能更大，必须用真实样本测平均/高分位体积。万级/日相应约为此值的百分之一，不能把该估算当磁盘配置结论。

百万/日满负荷持续一年约 3.65 亿条请求；永久保留意味着持续增长，不是撑过一个月就完成容量目标。压缩文件可以降低副本体积，却不消除主库和使用日志长期容量规划。

投影维度保持“用户 × 小时/日 × 单位版本”，不叠加模型、API Key、渠道、节点等高基数维度；按有数据的桶保存，空小时由服务层补齐。数据库索引至少覆盖用户+序号增量、用户+时间游标、队列领取/重试、账期唯一性、清单定位，避免盲目给所有字段建索引放大写入。

### 10.2 待执行的真实测试矩阵

| 维度 | 初始测试场景 | 必须记录 |
| --- | --- | --- |
| 数据规模 | 万级/日与百万级/日各一组，至少 30 日历史 | 表/索引/文件大小、扫描行数、执行计划 |
| 流量 | 持续流与突发分开；可先用 100 QPS 持续、500 QPS 短突发作为候选场景 | 成功率、结算吞吐/P95/P99、锁等待、DB CPU/IO；这些值不是用户已给的 SLA |
| 用户分布 | 分散账户；单一账户占 80%；单账户集中极限 | 钱包/账户序号行锁竞争，不只测平均分布 |
| 并行工作 | 结算、实时日查询、月预览、日志投递、封存并行 | 前台退化、后台积压和恢复速度 |
| 归档 | 每日百万条持续封存；月合计约 3000 万条，含首期截取/大抬头 | 内存峰值、块大小、对象数量、速度、故障续跑、源库读负载 |
| 长期保留 | 独立容量试验验证更长历史与索引增长影响 | 存储增长、备份/恢复耗时、是否需分层；不冒充已测全年容量 |
| 故障 | DB/Redis/日志库/存储失败，租约失效，分块/确认恢复 | 不重复扣费、不漏数、不错误发布 |

初始体验目标：已完成日查询 P95 < 1 秒，月汇总预览 P95 < 3 秒，小型 PDF 渲染 < 10 秒；正常增量汇总尝试控制在数秒内，出单要求完全追平。积压或千万级封存单独报告完成进度，不把汇总预览时延当作全量归档时延。

压测放在独立性能环境/脚本，不给普通单元测试加入随机大循环、sleep 或脆弱的机器耗时断言。功能测试用确定性金额和可控制的事务屏障验证不变量；性能报告必须附硬件、MySQL 版本/参数、数据分布、负载方法和实测结果。

### 10.3 什么时候才增加中间件

- MySQL 与后台 worker 先承担事实写入和增量处理；需要提高并发时先看索引、连接池、批次及热点锁，不能用日请求量直接推导必须分库。
- 私有 OSS 优先用于大量不可变文件，隔离归档 I/O 与主库大字段；需要新接入或权限配置时单独验证。
- 读副本只能在明确追平水位和一致性约束后承担读负载；不能从延迟副本签发一份看似完整的账单。
- 只有出现大量独立下游订阅、跨服务消费或主库队列实测瓶颈，再评估 Kafka 等持久消息系统；仍保留同库 outbox 和消费幂等，不以跨库双写替换它。
- ClickHouse 等分析库可服务额外的大范围分析，但不是一期单账户日/月账单的必要条件，也不作最终资金或凭证来源。
- 长期存储触及容量阈值后可另行设计热冷分层或分区/分片；要求完整数据持续保留且历史查询可用，迁移先复制、校验、切换。不能以容量优化名义直接清除使用日志。三库兼容接口保留，MySQL 专属方案不能成为所有部署的唯一实现。

### 10.4 一主一从是否能支撑

工程判断：以当前约千条记录、预期万级请求/日，不需要因本功能立即分库分表，规格合理的一主一从是充足的起步架构。百万请求/日也优先用同一架构验证，不先增加分布式数据库；但不能在未知硬件、峰值与真实行大小的情况下承诺现有实例已经满足目标。持续多年百万/日的主要新增问题是存量、备份恢复时间及索引工作集，而不仅是日均写入速率。

| 负载假设 | 平均请求/秒 | 连续一年请求数 | 判断 |
| --- | --- | --- | --- |
| 1 万/日 | 约 0.116 | 365 万 | 优先做好查询/连接池/持久性，无需提前分片 |
| 100 万/日 | 约 11.6 | 3.65 亿 | 一主一从仍可作为验证方案；需真实突发、热账户、归档并行和长期容量试验 |

上表是请求数，不是数据库 QPS；一笔请求有多个事务/行变动，补扣退款还会增加事件数，不能把 11.6 当成 MySQL 的全部负载。

建议职责分配：

| 组件 | 一期职责 | 边界 |
| --- | --- | --- |
| MySQL 主库 | 资金/账务写入、汇总写入、当前账单查询、下发/确认/作废与权限判断 | 所有强一致事务始终在同一主库；不把余额读随机分配到从库 |
| MySQL 从库 | 完整热备；经验证和限速的备份/历史只读任务 | 要能接管主库，不能仅为省成本配置无法承载写入的极弱从库 |
| Redis | 短缓存、可丢失的唤醒提示 | 不作唯一事实、任务或备份来源 |
| 私有 OSS | 固定明细块、可选 PDF、保护副本 | 文件永久保留，禁止到期删除，主库保留可鉴权定位的清单 |

第一阶段甚至不需要为了减轻约 24/31 行的账单查询就引入读写分离。后续若历史搜索/封存读取需要从库，必须先证明该从库已应用目标事务水位，再读取固定范围；重试不能随意跨不同延迟的从库。月单最终提交和用户确认仍回主库。

源码 [model/main.go](../../model/main.go) 当前只有 `SQL_DSN` 与独立可写的 `LOG_SQL_DSN`，没有专用只读副本路由。`LOG_SQL_DSN` 用于写日志，不能指向只读从库来实现读写分离。`common.IsMasterNode` 是应用节点的迁移/任务角色判断，也不是 MySQL 主从识别或故障转移机制；部署热备不会自动让现有查询分流。

从库复制同一份数据并应用主库写入，因此不是把总容量分成两半，也不会让主库扣费写入吞吐自动翻倍。主从配置还不等于自动高可用：需托管高可用入口或明确的故障检测、旧主隔离、晋升、路由切换和重试协议，避免双主同时接受扣费。

MySQL 默认异步复制可能存在提交与从库应用之间的延迟。半同步可增强已提交数据的保护，但其确认是接收并持久记录复制事件，不是已完成查询可见的应用；超时还可能退回异步，必须监控降级并制定策略，不能宣称天然零 RPO。[MySQL 复制说明](https://dev.mysql.com/doc/refman/8.4/en/replication.html)、[半同步机制](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)。

如果以“已成功的扣费在单机失效后也不能丢”为生产门槛，建议优先使用有明确持久性保证的托管高可用 MySQL，验证降级和故障切换；普通异步一主一从不能直接承诺这一点。仅有两个节点时还需考虑从库维护/故障期间的单副本窗口；性能能支撑与容灾保证是两件事。

### 10.5 是否需要调优：先做基础治理，不盲目升配

当前千条/万级日量没有证据表明必须立即增加服务器规格。需要的是可审计的数据库基线，以及与新账务协议一起交付的索引、查询和后台并发控制；本轮未连接生产数据库，不把源码默认值当成生产实测值。

| 优先级 | 项目 | 建议 |
| --- | --- | --- |
| 必做 | 索引与 SQL | 新账务表使用用户+账户序号、用户+入账时间+序号等联合索引；日/月只读投影；按真实查询 EXPLAIN，避免深 OFFSET 和无界月日志 SUM |
| 必做 | 连接池预算 | 按所有应用实例、独立主/日志/未来只读池的总和限制连接数，给迁移、复制、运维留余量；不是单纯调大 MySQL `max_connections` |
| 必做 | 事务与锁 | InnoDB、固定锁顺序、短事务、后台批次上限；归档压缩/网络上传不得持有资金锁 |
| 必做 | 持久性 | 核实 `innodb_flush_log_at_trx_commit=1` 与 `sync_binlog=1`，不以放松刷盘换取漂亮吞吐 |
| 必做 | 观测 | 慢查询、DB 池等待、锁等待、复制延迟、磁盘/IO、后台积压，先定位再调整 |
| 按实测 | 内存/磁盘 | 足够内存覆盖活跃索引/数据工作集，SSD 与可靠 IOPS；不是要求全部历史数据常驻内存 |
| 按实测 | 专用读负载/日志隔离 | 历史检索或日志索引实测挤占主库后再隔离，不为约千条记录新建分析集群 |

已有 `logs` 结构包含用户+时间+ID、类型+时间+ID 等索引，并非完全没优化；应检查生产迁移是否具备这些索引、执行计划是否使用，不重复加等价索引。旧日志列表仍含 OFFSET/计数查询，大数据压力测试必须同时覆盖旧页面，不能只证明新账单页快。[日志模型与查询](../../model/log.go)。

**已发现的配置检查点：**[model/main.go](../../model/main.go) 当前每个独立池默认 `SQL_MAX_OPEN_CONNS=1000`、`SQL_MAX_IDLE_CONNS=100`、连接寿命 `SQL_MAX_LIFETIME=60` 秒。最大连接数是上限，不代表启动即打开 1000 个；但多实例及独立日志池会放大总预算。没有独立 LOG_SQL_DSN 时主/日志共用一个池，不应重复计数。

可先在测试环境以每个写库连接池 `max_open=50`、`max_idle=10` 为起点，后台 worker 限制在 2–4 个；再看 `DB.Stats` 的等待次数/时间、查询时延和服务器活动连接调整。最终总预算须低于数据库允许上限并保留运维空间。连接寿命可评估从 60 秒调整为例如 300 秒，但必须小于相关代理/网络的连接生存限制，并核实实际断连规律；没有生产配置前不直接下发参数。Go 官方说明池达到上限会等待连接，池过小同样可能造成等待甚至错误的嵌套事务死锁。[Go 数据库连接管理](https://go.dev/doc/database/manage-connections)。

缓冲池按数据库可用内存及其他开销预算；独立数据库节点可先以约 60%–70% 内存试验，共享宿主机或容器不能照搬宿主总内存比例。MySQL 官方给出常见 50%–75% 区间，仍需根据实际工作集调整。[MySQL InnoDB I/O 优化](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-diskio.html)。

持久性参数的建议来自官方复制配置说明；这些参数不替代可靠磁盘和故障演练。使用托管数据库时遵循其参数支持范围及持久性承诺，不擅自更改受管配置。[MySQL binlog 与提交持久性](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html)。项目已有 `SQL_SLOW_THRESHOLD_MS`（源码默认 200 ms）；可与数据库侧语句摘要结合分析，但勿将含税号等敏感绑定参数的 SQL 散发到普通日志。

若要新建压测环境，可把当前量级的 4 vCPU/8–16 GiB、百万/日验证的 8 vCPU/16–32 GiB 每节点作为候选起点，均配可靠 SSD，主从能力相近。它们是实验档位，不是实测的最低配置、采购结论或对现有实例的升级要求。磁盘用实际“所有表+索引+日志+峰值临时空间+保留周期”估算，不用前面的 500 字节示例直接选盘；扩容窗口与备份副本空间另留预算。

### 10.6 旧归档、历史数据分别怎么处理

| 数据类别 | 一期保存方式 | 历史查询与长期处理 |
| --- | --- | --- |
| 现有使用日志、已采集调用记录 | 继续保留原 MySQL/日志库存量，不清理 | 历史使用日志按原权限查询；扫描评估缺口，不靠归档 PDF 代替完整日志 |
| 新账务原始 entries、资金凭据 | 主库持久保留，从库复制；另有备份 | 活跃/近期下钻读索引；正式旧单优先读取固定云端明细，不每次回扫主库 |
| 日/月汇总、单据元信息、清单、主体/确认版本 | 长期保留 MySQL | 体积相对小，维持列表、日期查询、追溯和鉴权 |
| 固化明细块、PDF | 私有云存储或小规模主库兼容存储 | 不重算、不覆盖；按访问频率转换存储类型，生命周期禁止删除 |
| 旧系统完整性不足的账目 | 保留原始资料，标记参考/未核验 | 未经补证不能出具覆盖完整的正式历史单据 |
| 数据库备份和 binlog | 独立备份策略与可恢复时间窗口 | 是故障恢复材料，不是用户可查询的永久业务档案；不把永久保留理解为所有恢复日志永不轮转 |

云端可以永久保存封存明细，但这并不自动减少主库源记录体积：一期存的是独立、可验证的对账副本，主库原始记录仍保留。这是对“使用日志不能清理”的保守落实，不暗含 90 天后 DELETE 或 DROP PARTITION 的任务。

**已固化文件：**建议最近 90 天保留标准存储，超过 90 天根据真实访问率评估低频访问存储；90 天是成本评估起点，不是数据保留期限。用户仍需即时下载的原始/确认 PDF 可一直使用标准存储。低频存储支持实时访问，但存在取回费、最小存储时长/计费大小等约束，不能只比较单价。冷归档/深度冷归档若需要解冻，应有“申请取回、处理中、可下载”的产品流程；一期不让历史下载突然变成需等待恢复的操作。[OSS 存储类型](https://help.aliyun.com/zh/oss/user-guide/overview-53/)、[存储类型转换规则](https://help.aliyun.com/zh/oss/user-guide/convert-storage-classes)。

存储类型转换必须保持原字节/哈希及明确的对象版本引用；如果使用复制到新对象的方式，先校验并切换存储定位，不修改账单正文/确认绑定。不能把对象存储前缀设为公开或复用具有到期清理的媒体目录。

**旧系统账目：**先保留现状并建立历史清单，核对日志开关/删除区间、已知充值与资金基准、任务扣退费和来源；完整资料通过独立导入批次、指纹与幂等规则回填，核验通过后才可为尚未出首单的用户设置更早起点。已出首单仍遵守起点锁定，需另行更正流程。无法核对的记录仍保留供查询，但标注参考，不按当前价格重算、不补零伪造完整性。不能因用户现在选择一个过去时间就自动认证全部历史有效。

**长期百万/日的源库存量：**建议先扩容与优化读路径，并按增长预测提前立项历史存储层。在数亿行或恢复窗口受压前评估按月历史库/表、完整日志归档与全局索引；不能把“金额正确的脱敏对账明细”当成“完整使用日志”的等价替代，它可能没有全部使用字段。

未来若要将源记录从热库搬出，必须另外确认保留政策与实施范围：完整复制 → 行数/金额/内容校验 → 独立保护副本 → 查询路由/恢复演练 → 可回退切换；所有正常查询、历史请求 ID 查找、退款原记录引用、重放校验及全局幂等均须继续可用。仅有云端文件而没有跨历史层检索和幂等方案，不允许回收 MySQL 旧副本。本版不执行、也不默认授权这种回收。

时间分区不是第一步，也不是无限容量方案。MySQL 要求分区列包含在每个唯一键中；直接给本方案的 `(user_id, account_seq)`、operation 去重键加月份，会改变跨月唯一性的保护范围，必须有全局幂等/目录约束，不能为了分区削弱“不重复扣费”。分区或分表实施还需兼容 SQLite/PostgreSQL 的替代方案。[MySQL 分区与唯一键限制](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations-partitioning-keys-unique-keys.html)。

### 10.7 运维门槛与演进触发点

主从不是独立备份：主库误操作可以复制到从库。建议有定期一致性备份、连续 binlog 保护与至少一个独立故障域的副本；恢复时间窗口可先按 30 天评估（最终按业务要求/成本确认），保证窗口内基础备份和所需 binlog 连续可用。用户业务档案仍永久保留，不受这个恢复窗口限制。时间点恢复是在基础备份上应用后续变更，恢复结果仍要与云端清单/确认记录核对。[MySQL 时间点恢复](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery.html)。

可用以下初始阈值触发排查/扩容评审，而非自动删数据或盲目改参数：

- 数据盘使用率达到约 70%，或按实际增长预计 90 天内触及安全上限：审查扩容和临时/备份空间。
- 代表性高峰中，DB CPU/IO 长期接近容量上限、连接等待或账单 P95 持续超标：先看慢 SQL/锁/后台竞争，再决定升配或读负载隔离。
- 汇总延迟持续超过 30 秒、封存未能在下一个日周期前完成、复制积压不能及时恢复：限速低优先级任务、定位瓶颈，不能简单增加无限 worker。
- 恢复演练超过约定 RTO、长期数据使重建/迁移无法在维护窗口内完成：在源库撑满之前评审历史存储层。

最终数据库参数需取得 MySQL 版本、主从每台 CPU/内存/SSD 与容量、应用实例数、日志是否独立落库、真实峰值和账户分布后落定。上述结论不要求立即采购更大实例，也不等于已经完成生产调优。

## 11. 上线门槛、监控和剩余确认

### 11.1 实施顺序

1. 日志不清理/不可关闭政策落地，检查并阻止遗留删除任务和旧节点；明确现有历史覆盖缺口。
2. 主库持久操作、管理员资金记录及全部请求/异步计费入口接入，三库事务和迁移验证；排空旧资金批次后确定技术采集起点。
3. 增量投影、准确首小时边界、资料版本和日查询，故障重放与并发测试通过。
4. 日逐笔封存、清单校验、不可变正文/PDF、权限/确认/异议闭环；所有文件完成才可下发。
5. 备份恢复演练、代表性容量试验、受控用户真实核对通过后开放正式出单；不能先上页面再把可靠记账列为后续优化。

现有 SystemTask 同类任务 active key 唯一，可复用一个扫描型调度器，内部按持久作业表和租约处理多份账单；不要直接给每份 PDF 创建互相冲突的同类 SystemTask。额度实时事务与后台任务使用独立并发预算，不能依赖 Redis 或单进程内存保证调度不丢。

### 11.2 必须有的观测指标

- 资金与 entry 差异数、未决 operation 数/最老等待时长、重复操作冲突、序号缺口。
- 各账户汇总未应用条数、最老未投影事件年龄、worker 失败/租约冲突、首小时边界状态。
- 使用日志 outbox 待投递数量/年龄、归档待办天数/字节数、失败块/校验差异、PDF/通知状态。
- MySQL 事务延迟/锁等待、连接池、磁盘/索引增长、归档存储增长、备份成功时间及最近恢复演练结果。
- 非法关闭/删除尝试、跨账户查询拒绝、关键配置/主体修改和确认审计；日志本身避免复制敏感税号与原始数据。

报警应可定位到账户/日期/操作/作业，不能只有“系统不健康”。确认/下载不因为外部通知失败被回滚；资金结果不明、归档损坏等风险需明确阻断受影响的正式操作。

### 11.3 评审边界

D1–D7 的业务方向、可靠记账和固化方案已获得用户无异议反馈，无需重复选择。本版进一步明确：一主一从作为承载架构、基础调优优先、旧数据不清理、固化文件可放私有云存储；实际参数与生产承载结论仍需部署信息和验证。

后续实施前核实实际 MySQL 版本/事务引擎与规格、峰值和账户分布、是否日志分库、现有 OSS/备份能力；这些缺失不阻碍本次设计，但影响最终容量参数和恢复承诺。WORM 锁定、生产配置更改、历史补录或热冷迁移有单独的变更范围，不能从“可以引入中间件”推定已经获准执行。

本轮仅更新三份设计文件，没有修改业务代码、生产数据库、日志保留设置或前后端依赖。待用户确认后再进入开发。
