# 素材渠道请求日志：MySQL 实施方案

状态：已实现。管理员可从素材渠道配置和同步任务进入请求日志界面。当前不要求 ClickHouse；未来可在数据量或检索需求超出 MySQL 能力时迁移。

## 记录范围

火山 Action API 和 YooFang REST 的统一请求边界，会记录手动“请求测试”及后台同步发出的每次上游请求。同步日志关联副本 ID、素材 ID 和渠道 ID；测试日志使用网关请求 ID 关联。HTTP 成功、上游拒绝、网络错误、响应读取或解析错误，以及发送前的限速和请求构造错误都有结果或错误类别。一次同步任务发出多个上游请求，就产生多条日志。

`asset_request_logs` 是独立于现有消费日志 `logs` 的元数据表。按日志 ID 查询时才读取 `asset_request_log_details`：该表保存请求地址、请求体、响应体及超限标志；响应状态码从元数据表读取。不采集请求头或认证头。JSON 敏感字段和 URL 中常见签名、令牌参数会被遮蔽；自由文本按已知令牌模式遮蔽，但无法保证识别所有非标准秘密。超出 16 KiB 的报文整体不保存，超过 8 KiB 的地址也不保存。详情是排障快照，不是可用于回放的原始报文。

## MySQL 存储与业务隔离

表使用现有日志数据库连接：配置 `LOG_SQL_DSN` 且其指向 MySQL 时，写入该日志库；未配置时现有项目的 `LOG_DB` 会回退主库。如果现有消费日志使用 ClickHouse，此素材请求表仍使用主库支持的关系数据库。要与业务库**物理隔离**，应将 `LOG_SQL_DSN` 配置到独立的 MySQL 实例；仅在同一实例分库或限制连接数，不能隔离磁盘和 CPU 负载。切换现有日志库配置前应评估旧 `logs` 数据迁移，因为该配置也控制消费日志。

业务调用只向 1024 条有界内存队列非阻塞投递，每 50 条或 1 秒批量写入两张表（同一事务），单批写入超时 2 秒。队列满或数据库写入失败会丢弃诊断日志，不影响请求测试和同步结果；失败批次在后端错误日志中限频报告。管理员接口返回**当前节点自进程启动以来**的累计丢弃数，不代表全节点总量。内存队列不保证崩溃前最后一批日志持久化，因此它是排障日志而非不可丢失的审计账本。

元数据默认保留 14 天，报文详情只保留 7 天。主节点每小时对两张表分别最多分 10 批、每批 1000 条清理过期记录，避免长事务和大范围删除；按时间、渠道+时间、副本+时间以及请求 ID 建索引。上线后应监控队列丢弃数、日志库写入延迟、表和索引增长、清理积压及业务库 CPU/IO，再决定是否拆分 MySQL 实例或迁移分析库。

## 查询与界面

仅根管理员可调用 `GET /api/asset-library/admin/request-logs` 和按 ID 获取单条详情的 `GET /api/asset-library/admin/request-logs/:id`。列表支持渠道 ID、副本 ID、来源、结果、请求 ID、时间范围和游标分页；默认最近 24 小时，最大时间跨度 7 天，每页最多 100 条，单次查询超时 3 秒。详情按需加载，不加入列表查询。界面提供最近 24 小时/7 天切换、来源与结果筛选、请求 ID 查询、翻页和刷新。渠道配置卡片上的“查看日志”按渠道打开；同步任务的“查看日志”按渠道和副本打开。数据库异常与“没有日志”显示为不同状态。

当前没有按节点聚合的丢弃指标，也不支持日志完整性保证、原始报文采集或跨库历史回填。如果将来需要高写入量、长保留期或跨大量记录的分析查询，应先基于运行指标评估 MySQL，再规划 ClickHouse 等日志后端；不必在目前提前引入。
