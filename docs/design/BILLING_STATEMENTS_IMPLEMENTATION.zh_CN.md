# 对账单一期：实施与验收说明

版本：一期开发交付及验收改进，2026-09-10。已 rebase 的代码基线 `9c37a6d`，开发分支 `codex/billing-statements`。操作步骤见 [验收指南](BILLING_STATEMENTS_ACCEPTANCE.zh_CN.md)。

本期只解决平台管理员与下游客户的服务消费对账。本文描述实际代码；此前的 [产品方案](BILLING_STATEMENTS_PRD.zh_CN.md)、[技术方案](BILLING_STATEMENTS_TECH.zh_CN.md)、[专项方案](BILLING_STATEMENTS_DATA_PIPELINE.zh_CN.md) 保留为完整设计基线，不应把其中所有扩展能力理解为本期已经实现。

本轮验收修正：历史空单防护、客户/操作人区分、版本化商务 PDF，以及明确确认后才执行的历史核验导入。实际边界见 [历史核验与统计说明](BILLING_HISTORY_REVIEW.zh_CN.md)。

## 1. 本期交付范围

| 使用方 | 已实现 |
| --- | --- |
| 用户 | `/billing` 页面；默认当天查询历史消费，按 24 小时展示消费、退款、净额并下钻请求明细；个人企业抬头/税号维护；已下发月单查询、确认、异议、PDF/明细下载 |
| 管理员 | 默认自己账户，可搜索切换客户；设置正式记账起点；月度历史参考与正式预览分开、逐项出单条件检查；创建存储归档草稿、审核后下发；状态筛选、异议回复、作废未确认版本、失败重试 |
| 凭证 | 冻结客户主体、币种/汇率、逐日金额、月总额和明细范围；私有 OSS 明细分片、正文快照、原始 PDF、校验清单；确认人、真实会话、时间与确认版本在主库留痕 |
| 基础保护 | 持久预扣/结算、钱包与账务事实同事务、幂等结算/退款；永久保留使用日志；服务端权限检查；7 种现有前端语言 |

页面入口同时接入个人资料与管理员用户操作中的“账单主体信息”。界面沿用项目现有 Base UI / shadcn 组件与查询缓存；列表采用游标分页，避免深页 OFFSET。

明确不扩展为：资金余额对账、应收应付、银行回单、税务发票、支付收据、电子签章、订阅/赠送多来源核算。确认不再次扣款。当前业务前提仍是管理员充值的钱包；若启用订阅等其他资金来源，不能直接用本期账单证明这些来源的全量消费。

## 2. 固定业务规则

- 时区：`Asia/Shanghai`（UTC+8），日期区间左闭右开，按实际入账时间归属。
- 正式起点：管理员首次启用时留空即使用服务器配置时间，也可指定一年内的未来时间；不能回填过去。首笔正式入账或创建任何月单后锁定起点。界面显示已设置的起点，不提供已启用起点的常规编辑。
- 起点之前的使用日志可查询历史参考，不会自动追溯生成正式消费账；独立历史核验导入须另行明确确认。常规正式首月只包含起点之后的入账。账户递增序号同时排除同一秒内早于配置动作的记录。日消费查询不受正式起点限制。
- 日查询按当前系统货币配置展示；正式月单在创建归档草稿时冻结配置。USD/CNY/CUSTOM 延用现有模式与符号；TOKENS 日查询显示额度，正式月单采用 USD 并在快照与清单保留 quota 换算。
- 金额 API 使用十进制字符串、固定 6 位小数；底层为整数 quota。总额按完整整数计算，另列非零“展示舍入差额”，不使用前端浮点数累加或 k/M 缩写。
- “记录数”包含消费与退款记录，正式账目还可包含受控调整记录，不宣称是去重调用数。
- 管理员充值/扣减/覆盖余额单独记结构化 funding 记录，不进入消费/退款总额；预扣冻结及失败释放也不算消费。跨期退款进入退款实际发生期。
- 当前月可预览；月结束满 24 小时后才能创建正式归档草稿。确认期限固定为下发后 7 天，只作提示，不自动确认。
- 公司资料带乐观版本检查与审计；后来改抬头、税号、汇率，旧单不跟随改变。
- 对账单内容由管理员审核归档草稿后下发；一个用户同一个月只保留一个有效版本。未确认版本可说明原因后作废再开新版本，原版本不删除；已确认版本不能覆盖或作废。

## 3. 记账与查询的实际实现

新增主库表共 9 张：

| 表 | 用途 |
| --- | --- |
| `billing_accounts` | 起点、当前主体、资料版本、账户提交序号 |
| `billing_account_events` | 主体/起点变更审计 |
| `billing_operations` | 单次请求持久预扣、最终结算或释放状态 |
| `billing_entries` | 只追加的财务明细及管理员额度变动 |
| `billing_hours` | 每用户每小时的整数汇总，以及首末明细序号 |
| `billing_statements` | 月单版本、冻结快照、状态、哈希、任务租约 |
| `billing_statement_events` | 下发、异议、回复、确认、作废等审计 |
| `billing_artifacts` | 私有归档对象的类型、顺序、哈希、长度、笔数 |
| `billing_history_imports` | 历史来源指纹、批次、确认人/会话/时间、核验依据、额度总计、起点变更 |

钱包结算的顺序为：锁定用户 → 持久操作 → 钱包调整 → 锁定账户并追加账务明细 → 更新一个小时汇总 → 提交。失败则整体回滚；成功后失效用户缓存。账务不依赖 Redis 成功或进程内批量队列。请求预扣为零、最终差额为零也会正确结束持久操作；重复结算/退款不会产生第二次资金变动。

任务补扣/退款的额度标记与钱包变动、明细同事务，防止旧轮询结果重复退款。现行模型定价、quota 安全边界与 token 额度机制保留；token 限额统计和使用日志仍是现有子系统，不宣称它们与钱包构成跨库原子事务。

本期将完整方案中的异步投影简化为“同事务更新单个小时桶”，不引入日表、投影队列或消息中间件：

- 正式月预览/冻结读取 `(user_id, hour)` 索引下最多 744 行，再在 Go 内形成最多 31 个日期；历史日志不会补进这份正式预览。
- 创建草稿时，对正式明细执行一次按用户/月、正式起点/序号过滤的 MIN/MAX 查询，以账本事实冻结准确序号范围；不再仅依赖小时桶的首末序号，防止缺失首末小时汇总时漏出明细。归档按 `(user_id, sequence)` 每批最多 1,000 条读取，不从账户最早历史扫描，也不用 OFFSET。
- 独立历史消费查询基于已有 `(user_id, created_at, id)` 索引：单用户单日或单月、最长 31 天，缓存未命中时 SQL 按小时汇总，月度参考再由 Go 归并为每日。缓存为每个后端进程独立的 128 项 LRU、TTL 15 秒，并用 singleflight 合并同进程同一查询，查询超时 5 秒。不是 Redis 全局缓存、离线历史投影或 OSS 统计；未配置 LOG_SQL_DSN 时消耗的就是主 MySQL 查询资源。
- 小时请求明细只返回安全字段，按时间、ID、请求标识游标分页，每页 100 条；查询失败与无记录分开，未发生时间不显示为零。
- 快照只保留逐日金额和整数校验值，不把 744 小时明细塞入 MySQL TEXT，避免不必要的大行。
- 出单检查会拦住账期结束前开始、仍处于 reserved 的请求。金额结果不明时不会通过补零完成对账。
- 正式记录为空但准确覆盖区间内存在消费/退款日志时，预览返回 `historical_data_unreconciled`，创建草稿、下发和客户确认均阻断，旧空草稿也受保护。使用未缓存的索引范围存在性查询，支持精确到秒的首小时起点；真正无消费的月份仍允许零单。这不是对所有日志与账本逐条相等的证明。

上述设计降低查询代价，但用户级资金写入仍需串行锁，热点账户与磁盘提交延迟必须在实际 MySQL 上测量。并未宣称完成百万请求/日压测。

## 4. 归档、固化与下载

`preparing → draft → issued → confirmed` 是主要流程。归档失败进入 `failed` 可重试；`issued` 可转 `disputed`，用户核对后仍可确认；管理员可以回复。未确认版本允许作废为 `void`。

后台 worker 使用数据库状态、租约与条件更新抢占任务；每 5 秒检查、租约 300 秒、每 30 秒续租。云端 I/O 不在资金事务或月单冻结事务内；进程重启后可以重新处理未完成归档。

每份月单保存：

1. `details`：每片最多 1,000 条 gzip JSONL，包含账户内序号、入账时间、类型、整数 quota、冻结币种金额、请求标识和模型。不包含 API 密钥、请求正文或余额。
2. `snapshot`：与主库快照逐字节一致的 JSON，冻结抬头、税号、逐日金额、换算与舍入口径。
3. `pdf`：内嵌中文字体的原始两页 PDF（正文、逐日汇总），生成后不覆盖。
4. `manifest`：月份、用户、版本、准确账期与序号范围、币种、总笔数、消费/退款总额度、按顺序的分片哈希，以及正文与原始 PDF 哈希。
5. `receipt`：确认后的三页确认回执 PDF；首次下载时生成并保存，之后读取原文件。确认事件与服务器时间在点击确认时已写入主库，不依赖下载。回执附原始 PDF 与明细清单哈希，不替换原始 PDF。

新草稿冻结用户名、显示名称和 `pdf_template_version=3`。v3 在创建草稿前读取系统 Logo URL，将经安全校验、限量下载和缩放的图片字节与 Footer 纯文本固化到快照；未配置徽标时用版本化默认平台标记，未配置页脚时内容留空。图片抓取不占用账务锁，后续归档/回执不访问可变 Logo URL。保留企业抬头/税号、金额卡片、右对齐逐日表及确认附页，去除面向客户的换算口径说明；内部计算与元数据不变。模板缺省的旧快照继续走 v1，已有 v2 保持 v2，旧原件、重试及回执不被样式升级覆盖。历史单冻结导入批次和来源摘要；逐笔归档附来源日志 ID/指纹，仍不包含余额或管理员私有信息。细节与边界见 [历史核验说明第 4 节](BILLING_HISTORY_REVIEW.zh_CN.md#4-pdf-与旧证据)。

界面明确区分“对账客户”和“操作人”。客户 ID 使用单据所有者，不使用 created_by；旧单缺少冻结用户名时只读解析当前用户名。审计操作人批量解析用户名，不返回用户密码、邮箱等私有信息。

归档发布之前，独立遍历账务明细，并与冻结快照逐日、逐月核对消费、退款与记录数。任一项不符，不能进入可下发草稿。快照读取、下发/确认、归档构建都会进行快照摘要验证。

存储对象路径为 `billing/statements/<statement-id>/<kind>/<ordinal>-<sha256>`。上传禁止覆盖，上传后重新读取、检查长度与 SHA-256，再发布元数据；重试只可复用完全一致的内容。存储对象注册与配置编辑使用同一个配置行锁，并重新核对存储身份，避免并发改桶导致凭证失联。

下载走后端授权代理，不暴露永久公共地址或 OSS 凭据。每次读取均验证大小及哈希，损坏/截断不会作为有效 PDF 发出。每个文件限制 16 MiB；详情页首批最多返回 200 个明细分片按钮，更多分片可按编号下载。

对账单/确认回执的客户下载名称为 `月度对账单_YYYYMMDDHHmmss.pdf` / `对账确认回执_YYYYMMDDHHmmss.pdf`，分别使用创建时间与确认时间（Asia/Shanghai）。前端读取 UTF-8 Content-Disposition，不再用 UUID 覆盖；内部主键及归档路径不变。

确认要求账单所有者的真实平台会话、勾选确认、二次确认，并提交实际查看版本的 manifest 哈希。管理员不能代客户确认，个人访问令牌不能确认。确认事务只产生一次确认时间与事件；不是法定数字签名。

## 5. 生产存储与历史数据

直接复用现有存储配置与加密/环境凭据；当前项目实际可用的提供方仍为阿里云 OSS，未虚构 S3/COS 驱动。创建草稿前需选择一个启用的 OSS 配置。

上线前必须检查：

- 账单前缀保持私有，应用仅具有必要上传/读取权限；不能给公共读取权限。
- 现有临时媒体的生命周期删除规则不得覆盖 `billing/statements/`。本期账单对象不使用临时媒体 TTL，不进入应用清理与已删记录清扫任务。
- 保留有归档对象的存储配置、凭据及加密密钥；允许轮换凭据，但不得直接改原配置的提供方、endpoint、region、bucket。
- 建议按业务留存要求对专用归档存储配置防误删/不可变保护。应用代码中的禁止覆盖与 SHA 校验不是云端 WORM，也不能阻止云账号所有者的外部操作。本次没有替生产桶配置 WORM；其锁定与作用范围需要运维确认，不能误锁现有临时媒体。参考 [OSS 保留策略](https://www.alibabacloud.com/help/en/oss/user-guide/oss-retention-policies)。
- 需要即时下载的 PDF/清单不要直接转为需恢复才能读取的冷存储；本期未实现冷对象恢复任务。明细将来转低频/冷存储前，要先验证读取方式、恢复时间及费用。
- 私有数据库备份与对象存储备份应独立验证。SHA 用于发现损坏，不等于备份，也不能独自对抗同时修改数据库与对象的高权限攻击者。

历史处理是“保留原数据、追加正式归档副本”，不是清库：

- 原使用日志、旧日志引用的请求体数据不因本功能删除；早期日志如果本来缺失，不能伪造恢复。
- 新账务明细、操作与汇总继续留在主库；对账正文、明细和 PDF 另在 OSS 固化。没有实施自动删热库、分区淘汰或分库分表。
- 使用日志禁删覆盖 API、底层删除函数、历史清理任务及 ClickHouse 日志 TTL；旧的关闭日志配置会被忽略，新的关闭请求被拒绝。服务器诊断日志文件清理不是使用日志清理，保留原有独立操作。
- 原使用日志跨库写入失败仍按现有方式报错，本期没有把完整使用日志改造为持久 outbox；正式资金事实的完整性由同库账务明细保障。
- 确认后的业务更正只能另行核查、记录实际新期调整，不能修改已确认单据。本期不新建人工财务调账工作台。

## 6. MySQL 与部署建议

一主一从仍是本期合适的部署起点，不要求新建分析中间件。按目前日常万级规模，先做索引、事务、连接池和备份的基础检查；百万请求/日只是约 11.6 请求/秒的日均量，不能替代峰值与热点账户压测。长期年累计体量也应单独评估。

- `SQL_DSN` 必须指向可写主库。`LOG_SQL_DSN` 如单独配置，也必须指向可写日志库，不能拿它充当只读从库连接。
- 本期没有新增读副本路由。出单、确认、钱包与账单查询均以主库为准，不受副本可见延迟影响。MySQL 支持异步及半同步复制；不能仅凭“一主一从”承诺零丢失，需确认故障切换时的复制进度与 RPO。参考 [MySQL 复制说明](https://dev.mysql.com/doc/refman/8.4/en/replication.html)。
- 现有应用默认 `SQL_MAX_OPEN_CONNS=1000`、`SQL_MAX_IDLE_CONNS=100`、`SQL_MAX_LIFETIME=60`。不要因为新增账单功能直接增加连接数：按节点数量、独立数据库连接池数量、服务器 max_connections 与观测到的等待时间，收敛连接池预算，再压测。本文不擅自修改生产参数。
- 使用 InnoDB，结合实际内存与活跃数据/索引工作集配置 buffer pool，观察命中率、锁等待、提交耗时、磁盘延迟、慢查询、备份时长与复制延迟；不要照抄固定内存比例。参考 [MySQL buffer pool 配置](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool-resize.html)。
- SQL 使用 GORM 通用路径，锁通过 `model.lockForUpdate` 适配 SQLite/MySQL/PostgreSQL；没有依赖 SKIP LOCKED、MySQL JSON 类型或时间分区。本机 SQLite 测试已通过，但仍需实测目标 MySQL 与 PostgreSQL 迁移，不将可编译当成三库验收。

推荐部署顺序：

1. 备份数据库与现有存储配置，确认测试库与生产库隔离；先在模拟生产 MySQL 执行迁移。
2. 低峰停止旧节点新请求，等待旧请求、异步记账与内存批量额度更新排空；统一升级所有参与计费的节点。不要长期让旧节点与新节点混合写同一钱包。
3. 按项目原有主节点迁移流程启动，新建上述 9 张表；所有节点完成升级并核对余额后，再逐个为用户启用正式记账。不要通过改历史起点来回避新旧采集边界。
4. 验证存储授权、生命周期、上传回读及下载；用隔离测试账户完成从结算到确认的闭环，再开放客户使用。
5. 回退时保留新增表和云端凭证，停止继续正式出单；不可删除证据表或直接降级后继续声称新期记账连续完整。
