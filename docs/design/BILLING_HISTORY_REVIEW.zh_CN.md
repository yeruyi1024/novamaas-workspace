# 历史账目核验、空单防护与统计计算说明

日期：2026-09-10；范围：平台管理员与下游客户的消费对账，不扩大为余额总账、银行收付款或发票系统。本文仅保留通用问题与操作规则，不公开测试环境中的客户信息。

## 1. 本轮问题的原因

历史月份的使用日志中已有消费/退款记录，但正式账本为零。修改记账起点不会自动补录过去的日志；旧代码错误地允许将这种差异生成零单。现在此情况返回 `historical_data_unreconciled`，不显示正式零月单，并在创建、下发、确认入口阻断。检查精确覆盖区间，不误拦起点之前的消费；真正无记录的月份仍可出零单。

草稿所属客户与审计操作人 `created_by` 是不同字段。现在分别显示客户用户名/ID 与操作人用户名/ID，二次操作确认也带上客户，避免混淆。

## 2. 历史核验导入的确认边界

流程：只读核验 → 填写依据与勾选授权 → 二次确认 → 云端来源固化并回读校验 → 主库原子补录。仅打开核验页不会写账本、导入批次或 OSS；本轮开发不替用户实际导入、作废或下发真实客户单据。

1. `GET /api/billing/admin/history-review` 按单客户、单月读取稳定 ID 的关系型日志。只取原始整数 quota、消费/退款类型、日志时间、请求标识、模型、令牌 ID；不读取或归档请求体、IP、令牌名称及管理员私有 other 字段。最多返回 31 日汇总，不在浏览器加载上万条记录。
2. 来源摘要覆盖原记录以及账户版本、序号和币种快照。`POST /api/billing/admin/history-imports` 要求真实管理员登录会话、明确授权、核验依据、同一摘要与幂等 ID；确认时重新读取来源，任何变化须重新预览核验，不能直接按旧金额提交。普通客户和个人访问令牌不能导入。
3. 原始依据压缩成私有 JSON 来源文件，复用永久账单存储用途，上传后回读验证大小及 SHA-256。`source_sha256` 为未压缩的完整来源快照摘要，存储对象另外记录压缩字节摘要；下载验证后者，解压后可核验前者。管理员可在“历史导入记录”下载依据。
4. 云 I/O 完成后才锁 User → BillingAccount，主库再次检查预览中的版本和序号、目标月份无正式明细/汇总、无未结算操作、无活动单据。并发结算或创建草稿会让旧核验失效。明细、小时汇总、批次与账户审计在同一事务提交，失败整体回滚。
5. 导入明细使用 `history_usage/history_refund`，保留原日志时间和有符号整数额度；记录批次、来源日志 ID 和单条指纹，正式 JSONL 明细可追溯。**不调用钱包扣费、令牌额度或使用统计更新**，WalletDelta=0。内部余额字段标注“导入时未变余额”，不假造历史逐笔余额；客户导出明细不含余额。
6. 批次永久留存确认人、真实会话、时间、核验依据、整数总计、起点前后值和来源对象。相同幂等 ID 的成功重试返回原结果；不同 ID 也不能再次导入同一客户/月。
7. 起点默认不变。仅当账户尚无任何账本提交、且无非作废单据时，此独立确认流程可显式建立更早起点；界面展示前后值、事务保留审计。不会悄悄扩大已记账客户的覆盖范围。现有空草稿需管理员明确作废，不覆盖归档。

限制及故障边界：

- 在线入口每月最多 10,000 条，读取上限 10,001 条用来检测超限、5 秒查询超时；主库每批写 100 行、事务最多 15 秒，小时汇总最多 744 行。超限明确拒绝，不把截断的记录作为完整月份。大型或已有新账目混入的月份需另行设计分段、可恢复迁移；这不是实时新账务的容量上限。
- 云端失败、来源变化、事务失败不产生部分正式账目。已固化但主库提交失败的来源对象保留供同 ID 重试和审计，不自动删证据。
- 日志库与主库没有分布式事务。导入的是管理员确认的冻结集合，不承诺包含在核验边界之后追加的旧月日志；有正常在途请求时首先阻断并核查。补录日期依原日志时间，不虚构已经无法复原的旧结算时间。
- 哈希证明归档后未变，不证明历史采集天然完整。旧日志有缺口或歧义时，管理员必须核对消费、退款和管理员充值依据；不能以勾选替代核验。本流程不复原历史余额、历史货币汇率或税务凭证，也不按今天的模型价格重算旧用量。

## 3. 小时和每日统计是否实时使用 MySQL

| 场景 | 实际路径 | 查询代价 |
| --- | --- | --- |
| 消费查询的小时统计 | 单日使用日志，缓存未命中时 SQL SUM/COUNT/GROUP BY 小时 | 使用日志库实时聚合资源，按用户及时间索引限定范围 |
| 月度历史参考的每日统计 | 单月日志先由 SQL 聚合小时，再由 Go 归并每日 | 仍有日志库实时聚合代价，不是离线日汇总 |
| 正式月预览 | 每次正式结算在钱包事务中增量更新 billing_hours；读取最多 744 行 | 小表索引读取，不现场聚合全部请求日志 |
| 已归档月单和下载 | 主库冻结快照/状态，OSS 固化 PDF、明细及清单 | 不重算旧月数据；读文件并校验摘要 |

历史缓存为每进程独立的 128 项 LRU、TTL 15 秒；singleflight 合并同进程同键请求，数据库查询超时 5 秒。不是 Redis 全局缓存、后台异步历史预聚合或 OSS 计算。未配置独立 `LOG_SQL_DSN` 时，这部分使用主 MySQL。OSS 优化的是凭证/明细文件存储与下载，不替数据库承担小时或日聚合。

本轮未调整 MySQL 全局参数、新增读副本路由、历史汇总后台任务或中间件。当前实际数据量可用于功能验证，但没有进行目标量级压测，不能据此承诺一主一从的吞吐量。后续若历史查询成为热点，可增加可重建历史汇总投影或只读日志库，必须单独验证历史补写、退款、更正和缓存失效边界。

## 4. PDF 与旧证据

2026-09-10 起，新草稿冻结 `pdf_template_version=3`、客户用户名/显示名称与平台名称，以及系统 `Logo` 图片的规范化 PNG 字节、`Footer` 的纯文本内容。v3 保留商务抬头、三项金额卡片、右对齐逐日表、文件编号、指纹及独立确认回执；历史导入单注明来源。原始两页，确认回执三页，不冒充发票、银行凭证或法定签章。

系统 Logo 未配置时使用版本化默认平台标记；已配置但读取失败、格式不支持或被抓取安全策略阻断时明确拒绝创建，不悄悄换用错误品牌。支持 HTTP(S) PNG/JPEG/GIF/WebP 图片，以及相对 ServerAddress 的站内绝对路径。网络请求在账务锁之外，最多 30 秒、2 MiB；拒绝超大像素图，按比例缩放为最多 24 KiB 的 PNG，快照总量限制 60 KiB，兼容现有 MySQL TEXT 字段。URL（包括可能的签名参数）不写入客户快照。后续归档重试和回执不重新抓取徽标。

Footer 去除 HTML 标记、脚本和样式后排版，不加载其中的外部资源；未配置时页脚内容留空，仍保留页码。页脚最多 300 字并受页面空间校验，不静默裁切。v3 不再展示换算率、quota 换算和舍入差额说明，但金额计算与存档中的换算依据保持不变。PDF 的项目来源元数据保留。

旧快照缺少模板版本时仍使用 v1，已有 v2 快照仍按 v2 渲染；旧原件及其重试不被新版排版覆盖。已下发/确认状态保存在平台审计中，不在原文件上改字。确认动作先保存时间和审计；首次下载确认回执时生成独立文件并归档，后续复用。

下载名使用 `月度对账单_YYYYMMDDHHmmss.pdf`（创建时间）与 `对账确认回执_YYYYMMDDHHmmss.pdf`（确认时间），均采用 Asia/Shanghai；重复下载名称稳定。HTTP Content-Disposition 用 UTF-8 编码，前端尊重服务端文件名，不再以内部 UUID 覆盖。此项也适用于旧单据下载，不改变内部 UUID、OSS 路径或已有文件字节。
