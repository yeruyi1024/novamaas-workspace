# 上游对账单设计与验收

上游对账单用于平台内部核对供应商消耗和成本。它将同一供应商的多个渠道归为一个会计主体，按上海时间查询用量，并冻结月度成本明细、PDF、Excel 和凭证清单。下游客户对账单继续使用原有客户账本和确认流程。

入口统一在原有“对账单”菜单，以客户对账单、上游对账单标签页区分。旧上游独立路径重定向至对应标签页；没有上游权限的用户只能进入客户对账内容。

## 上游归属和成本范围

管理员在“上游对账单”中建立上游名称并选择渠道，例如将渠道 19、26 归入一个上游。归属单独持久化，不改变渠道的路由分组、标签、模型映射或客户计费参数。每个渠道最多归属一个上游；修改上游时校验版本并记录操作人和成员快照。已生成单据保存生成时的成员，后续分组变更只影响新的查询和单据。

未配置 `cost_discount` 的渠道按测试渠道排除，零折扣 `0` 是有效的成本配置。已停用但仍配置成本的渠道保留历史消耗。统计读取消费、退款日志对应的不可变成本快照及追加成本更正，金额归属原发生日；客户销售费率的变化不直接替代供应商成本。

历史记录缺少成本快照或当时的成本折扣时，界面显示证据缺口，不用当前折扣反算过去。缺少日志的成本事实也显示为证据不完整。输入、输出、缓存读写和视频用量分别列示，视频任务最终用量按任务去重；退款和差额记账不重复计算一次请求的完整用量。不同协议的输入与缓存语义按原日志保留，各列不能无条件相加解释为供应商统一总令牌数。

历史按 tokens 计量的视频响应只有时长、没有最终 token 用量时，保留已知秒数并标记用量不完整，作为数据质量告警供核对。只有任务持久化提供方和终态响应明确证明按秒用量时，才使用供应商返回的实际秒数，例如阿里云任务的 `usage.duration`；不能根据当前模型配置、请求时长或按次计费开关把缺失 tokens 当作零。失败任务只有在同账期、同用户、同渠道、同任务的完整成本及退款证据证明上游净成本为零时，才标记失败已退款、用量不适用；客户已退款本身不能替代此证明。

原始任务提交没有 `task_id` 时，每条日志保持独立请求，不能以空任务 ID 合并。历史关联恢复只接受固定摘要的人工审核清单，并在事务内重验原件：提交秒、用户、渠道、令牌、模型、分组及价格一致，独立预扣/终态差额或全额失败退款证据闭合，且全范围双向唯一。接近时间、相等金额或终态金额减差额不能单独证明身份。审核关联追加在独立不可变表，保留规则版本、审核摘要、证据摘要、批次及操作者，不改原日志、任务、成本或客户金额，也不提供通用网页猜测绑定入口。

读取时再次验证来源与终态响应摘要；通过关联取得的真实用量明确标注为“审核关联恢复”，不表述为找回了原始提交响应。成功视频使用已有终态真实用量，失败仍须通过完整上游退款证明。日志数据库为 ClickHouse 时不使用这类依赖稳定日志行 ID 的关联。已冻结单据保持原件；新增关联只影响后续查询和新生成的单据。

## 查询和冻结

查询支持自然月，以及最长 366 天的自定义日期范围。日期使用 `Asia/Shanghai`，界面结束日期包含当天，后端转换为左闭右开的时间范围。页面提供总计、逐日、按模型及日期和模型交叉汇总，并可查看分页的安全逐笔记录。

实时逐笔查询的数字游标会重新扫描前页，单次查询限时 20 秒；大范围查询可通过日期或模型缩小范围。正式归档明细使用冻结记录的索引分页，不受实时查询的前页重扫影响。

金额在后端使用整数额度和十进制换算，API 返回六位小数的字符串。消费成本和退款成本分别以正额展示，净成本为两者之差；前端不累加浮点金额。模型名称按精确字符串分组，避免数据库大小写排序规则合并不同模型。所有总额和用量累加都检查精确数值边界。

渠道用户成本分配展示每个渠道中各用户的成本消费额、退款、净成本和请求数。占比为用户净成本除以该渠道净成本，使用未舍入额度计算并保留四位百分数；渠道净额不为正或有成本缺口时占比为空。退款可能使某用户占比为负或超过 100%，不做截断。未知或已删除的用户仍保留原用户编号，避免漏算成本。每行重复的渠道净额只作为分母，不可重复加总。

新生成的单据使用快照版本 2，冻结渠道用户分配及安全名称，归档时从冻结逐笔记录独立复核金额、用量和比例。PDF 增加分配明细，Excel 增加“渠道用户成本”工作表。旧版本 1 保持原件，不以实时数据补写历史分配。

正式单据以自然月为单位，月结束满 24 小时后可以生成。生成时重新统计数据质量，冻结上游名称、成员版本、历史成本、用量、逐日及模型汇总、币种、文档品牌信息、统计截至时间和全部告警。安全逐笔证据每批最多 1,000 条写入独立暂存表；最终主库事务核对组版本、成本配置、记录数和来源摘要一致性后发布单据，失败时清理本次未发布的暂存记录。归档重试读取冻结表，不读取后来变化的渠道、价格或任务内容。单据正文在 MySQL 使用 LONGTEXT，在 SQLite、PostgreSQL 使用 TEXT，以容纳逐日模型汇总和冻结品牌信息。

## 数据质量告警

缺失渠道、缺少历史成本、用量未知、估算用量和待结算任务均作为告警，不限制生成草稿、财务审核、确认或归档。`coverage.complete` 继续表示来源资料是否完整，不能因允许出单而改成 true；逐笔的缺失、估算及待结算标记也保持原值。这样可以先保存待核对的账期，财务结合供应商附件核实差异。

成本完整时正常展示金额；部分成本缺失时只合计已知成本，标示“已知成本小计”；全部缺失时显示“未知”，不能把没有金额证据解释为免费。合法零折扣、真实零成本仍按零展示。某渠道存在成本缺口时，用户占比保持空值，避免将部分分母当作完整成本。未知和估算用量分别标记，不倒推、不补造最终 tokens 或秒数。

页面、PDF、Excel 和确认回执展示数据质量告警及统计截至；有缺口的文件说明“用于核对，缺口待核实”。Excel 的每日、模型和渠道用户明细标出金额范围及用量状态，安全逐笔文件保留原始质量标记。确认表示财务审核了所绑定的文件与附件，不表示系统已恢复缺失的原始证据。后续证据恢复不重写旧单据或旧文件。

来源摘要不一致、冻结明细被篡改、金额或用量溢出、无权限、对象存储失败等仍属于操作或证据完整性错误，继续拒绝或重试；这些错误与可供财务核实的数据质量告警分开处理。不新增告警确认弹窗或额外审核步骤。

后台每小时清扫最多 1,000 条超过 24 小时的未发布暂存记录，并在删除时再次检查单据不存在，保护并发发布和所有已发布版本。没有创建时间的旧记录保留。

## 草稿确认与归档

状态为 `preparing → draft → confirmed`；归档失败进入 `failed`，可以重试同一冻结版本。未确认的草稿或失败版本可以说明原因后作废为 `void`，原件与事件保留。每个上游每个月只允许一个有效版本，确认后的版本保持只读。

后台任务使用数据库租约抢占和续期，逐批读取冻结明细，验证明细摘要以及日、模型、总计金额和用量。上传成功且回读校验一致后才发布草稿。文件使用现有阿里云 OSS 存储配置，保存为永久 `billing_archive` 对象，不进入临时素材的 TTL 清理流程。

| 文件 | 内容 |
| --- | --- |
| PDF | 上游主体、账期、成本消费/退款/净额或已知小计、每日和模型汇总、数据质量告警及统计截至 |
| Excel | 同一冻结内容的总览、每日、模型及用量汇总、金额范围、用量状态及数据质量告警 |
| snapshot | 冻结单据正文 |
| details | 每批最多 1,000 条的 gzip JSONL 安全逐笔证据 |
| manifest | 单据、正文、PDF、Excel、来源和各明细分片的 SHA-256 及精确校验值 |
| receipt | 确认后的独立回执，保留确认人、时间和所确认文件摘要 |

文件按上游、月份、单据、类型和内容摘要隔离，不覆盖已有对象。下载经过后端授权并验证长度与 SHA-256；客户端不获得 OSS 凭据或公开永久地址。确认回执独立保存，原始 PDF、Excel 和明细保持原字节内容。

确认及作废由拥有财务管理权限的管理员操作。确认要求真实登录会话、明确勾选并提交所查看版本的凭证清单摘要及审核附件清单摘要。这是内部财务核对记录；审核备注、确认人、会话和时间持久留痕。

财务管理员可在草稿审核时上传上游系统的原始账单附件，支持 PDF、XLSX、CSV、PNG、JPEG，单份最多 20 MiB，每单最多 20 份有效或上传中附件。附件可选；没有附件时也绑定空清单摘要。文件保存在本单冻结的 OSS 配置，保持永久、私有、不可覆盖，校验上传后回读的长度和 SHA-256，文件名、类型、上传人及时间一并留痕。

上传预留和最终确认锁定同一单据：上传中不能确认，附件变更使旧审核摘要失效，确认后不能新增或替换附件。上传失败保留审计；超过 15 分钟的未完成预留转为失败，避免进程中断永久阻塞审核。确认时冻结附件清单并绑定原始凭证清单；回执记录该审核证据摘要，原始 PDF、Excel 保持不变。

## 权限与接口

上游标签页、API 和下载要求管理员角色及 `financial_accounting.view`、`financial_management.view` 任一权限。财务核算可查看、维护上游分组及生成草稿；财务管理包含原财务核算范围，并可上传审核附件、确认及作废。只具有财务核算的管理员不能审核。普通客户即使被配置财务权限也不能进入上游模块。

新增财务管理权限默认不授予普通管理员，root 保持固有全权。团队编辑返回原始权限开关，登录和能力查询返回继承后的有效权限，避免取消财务管理后意外留下独立的财务核算授权。渠道读写、敏感编辑和其他板块权限保持独立，财务管理不会额外授予渠道编辑能力。上游单据使用独立的单据表和查询路径，客户对账单路径无法读取这些成本凭证。

API 位于 `/api/upstream-billing`：

| 路径 | 用途 |
| --- | --- |
| GET/POST `groups`；PUT `groups/:group_id` | 查询和维护上游归属 |
| GET `channels` | 搜索不含密钥的渠道选项 |
| GET `report` | 按月或日期范围汇总 |
| GET `usage-details` | 按日期和模型筛选的逐笔明细 |
| GET `storage-profiles` | 现有启用的 OSS 配置 |
| GET/POST `statements` | 月单列表和冻结草稿生成 |
| GET `statements/:statement_id` | 冻结内容、文件和操作记录 |
| POST `statements/:statement_id/actions` | 确认、作废、失败重试 |
| POST `statements/:statement_id/attachments` | 财务管理上传上游账单附件 |
| GET `statements/:statement_id/attachments/:attachment_id` | 授权下载本单已完成附件 |
| GET `statements/:statement_id/files/:kind/:ordinal` | 授权文件下载 |

## 验收范围

回归覆盖渠道排他归属和乐观锁、未配置成本排除与零折扣、历史成本与更正、退款、令牌及视频去重、时间边界、带质量告警的生成和归档、未知金额与已知小计、冻结后配置变更不影响原件、文件回读与摘要、篡改拒绝、失败重试、确认幂等和权限矩阵。下游原有对账单和永久存储保护需要一起回归。

本次开发已通过完整 `GOWORK=off make test`（包含独立 relaykit 模块）、后端编译及受影响包的 `go vet`；前端通过类型检查、相关回归和生产构建。

本地审阅使用独立 SQLite 的演示数据与生产导出代码生成样张。页面及 PDF、Excel 截图用于确认功能形态；模拟 OSS 传输测试用于验证签名请求、不可覆盖、回读、文件摘要和元数据写入。真实 OSS 存储配置的上传和下载验收须在已配置的隔离存储环境中进行。
